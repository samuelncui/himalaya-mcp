# Native metadata generation

`baseline.json` pins the first supported official release. It is a source baseline, not a moving latest-version pointer. Candidate locks and all downloads, source copies, dependency caches, compiled helpers, JSON, and reports live in ignored `build/`.

- `node scripts/upstream.mjs resolve --version 2.2.1` or `resolve --latest` writes `build/generated/upstream.lock.json`. It resolves the actual tag commit, checks Cargo.lock, verifies GitHub archive digests, computes binary digests, and checks the embedded version, revision, target and Cargo features of all five official binaries.
- `node scripts/upstream.mjs generate --lock build/generated/upstream.lock.json` rechecks those assets and source, then builds `entry.rs` in a temporary copy of that exact source with the same features. The official binaries stay unchanged. The published runtime contains no Rust code or parse helper.
- `node scripts/upstream.mjs verify` compares every upstream-declared command Help page with the host's official binary, checks aliases and explicit file semantics from `profiles/himalaya.yaml`, and compares the actual JavaScript schema/serializer with native parse results using `native-cases.json` plus automatically derived checks for every runnable command argument, repeated option occurrence and variadic positional shape. Only `--help`/`--version` run on the original binary; all command-argument checks use the parse-only CI helper. No mailbox is opened.
- `package` builds and packs the existing artifacts into `build/packages/`; `update` resolves the selected/latest release, generates and verifies without publishing or changing the baseline.

The exporter builds an independent discovery tree with Clap's global `disable_help_subcommand(true)` setting before collecting business paths. This materializes deferred registrations while suppressing automatic Help copies, including in child commands. Explicit business commands named `help` remain registered; names do not determine classification. A second normal tree retains native Help and the complete reflection structure. A node absent from discovery is accepted only under a proven automatic Help branch: its ancestor was generated from a parent with automatic Help enabled. An unmatched business path stops generation with that path instead of silently omitting a tool. `frameworkGenerated` marks Clap's completion Help copies; those nodes are metadata rather than separate executable MCP tools. For the initial release the derived summary is 938 reflection nodes, 235 source-declared paths and 188 executable paths, including the root command. These counts are observations, never compatibility constants.

For 2.2.1 the official release has ten features and omits `vendored`, although Cargo's default set includes it. Generation uses the features verified in all official binaries rather than assuming defaults.

The native parser owns groups, conditional requirements, conflicts, defaults and opaque custom parsers. The CI JSONL `parse` mode returns canonical paths and raw values/occurrence groups with their value sources; it does not serialize private validators or claim that raw values are typed parser outputs. `syntax-report.json` stops release verification on generic unsupported syntax or a source-declared path parameter without an explicit I/O role. New non-file commands register automatically; new file semantics require a factual profile declaration so an unknown output destination cannot inherit a generic input-path boundary. Schema checks use those same profiles. The fixtures check binding and schema compatibility, not email delivery or backend behavior.

`verification.json` distinguishes representative fixtures from generated field and array checks. Generated checks use native choices, synthetic fixture values and a small general sample pool; they assert canonical paths, raw value binding, occurrence groups, value sources and no unintended option activation. They do not reconstruct validators. A future opaque parser or native requirement/conflict can reject the available synthetic samples; the report records those native-validation rejections explicitly rather than counting them as successful binding checks. Unknown options, unexpected arity failures or a binding mismatch fail verification. Help/Version actions are checked through native Help/version checks, not as ordinary business arguments. These checks establish registered syntax and binding for the selected release, not arbitrary cross-field combinations, typed custom-parser normalization, terminal interaction, email delivery or backend semantics.

The generation helper has filtered Rust regressions for nested deferred registration, hidden deferred commands, explicit business `help` commands and fail-closed rejection when deferred registration changes with the Help setting. They use synthetic Clap trees and never invoke Himalaya's business executor.
